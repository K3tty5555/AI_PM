# 第三步：基于证据的视觉稿

适用于前两步布局/逐页反馈已确认后，用户要求产出贴近现网的视觉稿。该阶段不能重新选一套审美，也不能拿 AI_PM 工作台的 DESIGN.md 给业务页面换肤。

## 输入与先查项

1. 读当前 `prototype-spec.json`、有效审批、最近反馈和 active PRD，锁定页面、状态、栏位与业务文案。
2. 按项目配置 `designSpecPath` 定位产品 DESIGN.md。没有文件或只有一组通用颜色时，先依据实际页面建立模块 profile，不凭名称猜“已加载公司规范”。
3. 查视觉包的 `sourcePrd` / `sourceSpecHash`，不能只因 `status=ready` 就使用。旧版本视觉包只作有标记的辅助参考。多版本包通过项目配置 `visualPackagePath` 指向当前包，不覆盖历史包。
4. 实际网页与源码分开登记：源码 checkout 时间不等于现网上线时间；历史原型不是现网截图。用户授权浏览器后，按角色、入口、页面与数据状态采集截图和组件 computed styles；空数据时先尝试已有筛选和样例。

## 实现策略

- 视觉来源优先：本轮现网证据 + 用户确认的目标改动 > 对应模块源码和设计规范 > 带日期的历史截图 > 生成模型判断。
- 已确认业务结构必须保留。现网为双栏、目标已确认三栏时，明确列为 target delta，继承组件与密度，不擅自退回双栏。
- 模型需具备读图和修改代码能力；使用当前用户选定的模型并记录本轮实现方式。不要把模型名称或自评分当作还原度证明；没有相同输入的对照实验，就不声称某个模型导致失败或已被证明更强。
- 优先从确认后的 HTML 派生可编辑视觉稿，保留稳定 ID 和关键交互；渲染后导出 PNG。界面文字、表格、表单、状态由代码承担；不把整页生图当成真实 UI，也不强制让用户切模型或付费 API。
- 页面风格按模块 profile 分开。新版容器、独立管理页、教师阅卷及业务浮层不能全部用一套壳。
- 产物放项目 `06-prototype/visual/`（查看入口）和 `06-prototype-visual/<当前包>/`（证据映射、截图、审计）；可交互 HTML 可放 `06-prototype/当前版本/`，避免相对资源失效。

## 验证与交付

至少核对默认态、已确认关键状态、弹窗、长内容和目标桌面宽度；截图使用同一视口，并区分 source、approved prototype 与 target。每个关键帧记录页面错误、资源失败、横向溢出及截图 hash。

审计分开评价“未改区域的还原”和“批准改动的实现”，不给整图差异率强行打分。未验证状态、缺失现网数据、旧参考必须写清。只更新有业务或布局变化的 PRD 引用；视觉修正不改业务规则，不自动发布云端。

第三步入口必须指向实际产物；尚未生成时保留待产出提示。manifest 必须包含当前 spec hash、产品设计规范路径、模型/实现方式、逐帧 reference 与 target 文件、浏览器核验结果。用户才是最终视觉验收者。
