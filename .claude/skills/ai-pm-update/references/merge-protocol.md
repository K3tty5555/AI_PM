# 三方合并协议

## 三棵树

```
base   = 包内该文件的「上次发出去时」的历史版本
ours   = 用户当前目录
theirs = 包内新版
```

**引擎是 Claude 本身**：读三棵树、算差异、判冲突。没有外部脚本。

## 逐文件判定

| base | ours | theirs | 处理 |
|------|------|--------|------|
| 有 | 未改 | 改了 | 用新版（继承官方更新） |
| 有 | 改了 | 未改 | 保留用户的 |
| 有 | 改了 | 改了 | **冲突 → Claude 提「第四种方案」** |
| 无 | 有 | 有 | 用户新增 → 保留 |
| 有 | 无 | 有 | 用户删除 → 询问 |
| 有 | 有 | 无 | 官方废弃或改名 → 若用户改过则判冲突上报；未改过则随官方处理 |
| base 无此文件 | 有 | 有 | 按内容判断用户是否改动过；改过则保留，未改则用新版 |

**粒度**：行级。markdown 章节结构只作为「冲突发生时给 Claude 的上下文」，不作为对齐单位。

实测依据：章节级对齐会把行级能干净合上的报成冲突（多报假冲突）。

## 冲突处理

Claude 在冲突处**提「第四种方案」**（不是 ours/theirs 二选一），并说明理由：

> 我们这次改成了 X，你的改动在做 Y，可以合成 Z；若你的动机是 W，则保留你的版本。

**裁决结果呈现给用户，由用户决定接受哪些。** 不自动落盘。

## 结构化文件（`settings.json` / `.gitignore` / `.codex/hooks.json`）

不走行级合并——会产出语法错误。做法：

1. 解析两侧 JSON（或按行语义解析）；
2. 取并集（如 `permissions.allow` 数组取并集）；
3. **合并后校验**；校验不过 → 判冲突上报，**不落盘**。

理由：`settings.json` 解析失败会让 SessionStart / PostToolUse / Stop 三组 hook 全部静默失效，而 Claude Code 不会明显报错。

## 二进制文件

整文件替换，禁止行级合并。判定：文件含 NUL 字节，或扩展名在 `{png,jpg,jpeg,gif,ico,pdf,docx,xlsx,zip}`。

## 知识库卡片（`templates/knowledge-base/`）

同样走三方合并，但判定键不同：

1. **主判据 `auto-dedup-key`**（398 张卡里 335 张有）
   - 同 dedup-key → 同一张卡，走三方判定
   - 同 `id` 不同 dedup-key → 纯编号冲突 → **用户卡保 id，官方卡按该目录最大序号重编号**
   - 都不同 → 直接落
2. **`auto-dedup-key` 缺失的老卡**（63 张）→ 标题归一化 + 正文相似度兜底
3. **退役用软退役**：写 `superseded-by`；物理删除留给用户拍板

### 三条知识库铁律

- **`last-verified` 只能因真核实而刷新。** 合并动作本身不构成核实，**绝不能刷此字段**——否则污染 `review-stale` 的衰老信号。
- **合并必须幂等。** 现有 `merge A,B → B` 是 `cat 验证数据段 + rm`，跑第二遍会重复追加。跨库合并要加「这个版本的卡已合过」的锚。
- **可逆优先。** 软退役 + 并集落盘，物理删除必升用户。
