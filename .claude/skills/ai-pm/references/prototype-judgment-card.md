# Prototype Judgment Card

> 原型质量判断卡。用于 Phase 7 原型生成前的蓝图、生成中的约束、生成后的质量审计。

## 0. 两套哲学 + 防 bleed（指针，单一事实源在 prototype-agent）

**PRD = 说明书（要解释：做什么/为什么/规则边界），原型 = 镜像（零解释：用户真用起来啥样）**——两者在"解释"维度正好相反。写时反射、防 bleed 闸、分寸（AI 真话术留 / 评审 meta 挪走）**已内化到 `agents/prototype-agent.md` 核心信念 7 + 生成约束 + Mode B 步骤 3（visible-copy-audit）**，写原型时在那里 fire，本卡不双写。配套产物：交互/视觉规格只进 `06-prototype/HANDOFF.md`（设计师接手），不进 HTML 屏幕、不回 PRD 功能表格。

## 1. 原型目标

HTML 原型的标准不是"有页面"，而是"可评审"：
- 评审人能在 30 秒内看懂产品形态和主流程。
- 核心任务能被点击、切换、输入或确认走通。
- 页面有真实业务密度，不是营销模板或灰白卡片堆叠。
- 关键状态有呈现，尤其是失败、空结果、加载、成功反馈。

### 1.1 原型分级（默认即最高档：可操作级）

**默认目标 = 最高档（可操作级），它上面没有更高的档。** 凡是要给评审 / 老板 / 试点看的产品原型，一律按最高档做——这是基线，不是加分项、不是"有余力才做"。只有明确是一次性概念稿、纯内部碰撞时，才**有意识地**降档，并说一句"这次只做到 X 级，因为 Y"。

下表从高到低排列，**第一行（最高档）就是默认**：

| 档位 | 标准 | 何时用 |
|------|------|------|
| **可操作级 ·【最高档 = 默认】** | 在可评审级之上：能像上线后一样**自由操作**、占位按钮**做成真交互**、视觉推到**顶级**。判据见 §6 交互体验完整判据 + §9 反假原则；注入式原型另见 §10 视觉分面 | **默认**——所有正式产品原型 |
| 可评审级（降档） | "原型目标"四条：可评审 + 能点通 + 视觉可信 + 关键状态 | 明确降档：时间盒很紧、只配 PRD 走查够用 |
| 示意级（降档） | 布局/功能示意，能讲清形态 | 明确降档：早期概念碰撞、内部对齐 |

降档是有意识的取舍，要主动说明；不主动降、不默认停在演示级。完整工作流（尤其 fork 注入式）见本机知识库 `playbooks/PLAYBOOK-010`（本机沉淀，开源仓不含；要点已在本卡 §视觉分面 / §反假原则中给出）。

## 2. 生成前蓝图

生成 HTML 前必须先在内部完成以下判断：

| 项 | 必答问题 |
|----|----------|
| 页面/视图 | PRD 中哪些内容需要界面承载？哪些是无界面逻辑？ |
| 主流程 | 用户从哪里开始，经过哪些步骤完成核心任务？ |
| 信息层级 | 首屏最重要的 3 个信息是什么？ |
| 状态 | 默认、空、加载、错误、成功分别怎么呈现？ |
| 交互 | 哪些按钮/输入/切换必须有反馈？ |
| 视觉方向 | 产品场景要求高密度、轻引导、沉浸式还是工具型？ |

蓝图可以不单独展示给最终用户，但必须影响 HTML 结构和样式。

## 3. 视觉设计红线

以下问题任一出现，视觉设计不得分：

- 只有白底、灰卡片、蓝按钮，缺少场景化设计主张。
- B 端管理台做成大标题、大留白、营销落地页。
- C 端/移动端做成密集后台表格。
- 页面元素大小、间距、层级没有规律，像模型随手拼贴。
- 假数据明显敷衍：测试数据、示例内容、张三李四、无业务字段。
- 重要状态只用文字说明，没有可视化反馈区。
- 使用大量装饰性渐变、光效、卡片阴影掩盖信息不足。

## 4. 场景化视觉判断

| 场景 | 视觉策略 |
|------|----------|
| B 端 / 内部工具 | 信息密度高，导航稳定，表格/筛选/批量操作清楚，装饰克制 |
| 教育 / 教师工具 | 任务路径清楚，状态温和但不幼稚，数据和班级/题目/学生信息真实 |
| Agent / Copilot | 对话流 + 状态卡 + 结果预确认并存，用户能看懂 AI 做了什么 |
| C 端 / 移动端 | 轻引导，首屏路径明确，控件触达友好，情绪设计服务任务 |
| 数据分析 / BI | 指标层级、图表解释、筛选上下文、异常状态必须清楚 |
| 营销 / 品牌展示 | 可更强视觉记忆点，但不能牺牲主 CTA 和转化路径 |

## 5. Agent / Hybrid 原型专项

Agent 产品原型必须呈现 6 件事：

1. 用户输入入口：自然语言输入、快捷建议或指令入口。
2. AI 回复：不是纯文本说明，要有结构化结果或行动建议。
3. AI 状态：思考中、检索中、生成中、工具调用中至少一种。
4. 结果预确认：AI 做出决策前，用户能看到摘要并确认/修改。
5. 修改入口：用户能调整 AI 默认值、范围、筛选条件或下一步动作。
6. 失败兜底：数据不足、找不到结果、AI 不确定时给替代方案。

缺任一项，Agent 原型最多只能判"部分达标"。

## 6. 审计评分

每份原型按 12 分制审计：

| 维度 | 0 分 | 2 分 | 4 分 |
|------|------|------|------|
| PRD 覆盖 | 主流程缺失 | 主流程有但状态/子流程缺 | 页面、功能、关键状态覆盖完整 |
| 交互体验 | 静态展示或点击无反馈 | 可点击但流程断裂/反馈弱 | 可自由操作 + 占位做真 + 反馈明确（可操作级，完整判据见下） |
| 视觉设计 | 模板感强/层级混乱 | 基本可看但缺少场景真实感 | 视觉方向明确，密度、组件、假数据可信 |

判定（与 CLAUDE.md / phase-7 / prototype-agent 统一口径：总分 ≥ 9 且单项 ≥ 3 即可进评审）：
- 总分 ≥ 9 且单项均 ≥ 3：可进评审。
- 总分 < 9，或任一单项 = 2：修完关键问题再评审。
- 任一单项 < 2：必须重做或大修。

**交互体验 4 分完整判据**（默认按可操作级；下列任一不满足即扣到 2 分）：

- **可自由操作**，不是点一下看脚本自动播放——用户能自己驱动流程、改输入、看到对应变化。
- **占位按钮做成真交互**（展开全部、编辑、换一批、导出进度态…），不留"假装能用"的死按钮（见 §9）。
- **认有限意图 + 澄清兜底**，不硬解析任意输入（见 §9 原则 ①）。
- **改输入只重计数可见数字、大盘稳住**，不在演示假数据上假装全量重算（见 §9 原则 ②）。
- **人机确认是真检查点**：多步流程每道闸需显式确认才解锁下一段（可带自动兜底，让被动观看也能看完）。

> 仅当 §1.1 明确降档到可评审级时，这条线才放宽到"核心任务能点通、状态反馈明确"——且要说明为什么降。

## 7. 修复 punch list 写法

每条问题必须可执行：

✅ `首页首屏只有欢迎语，缺少教师当天任务入口 → 增加"待处理任务/最近考试/常用动作"三块，并给真实数量。`

❌ `视觉再高级一点。`

✅ `AI 结果只有一段文字 → 改成"摘要卡 + 依据列表 + 确认/修改按钮"，体现预确认。`

❌ `加强 AI 感。`

## 8. 不可越界

- 不把视觉像素、色号、动画毫秒写回 PRD 功能表格。
- 不要求最终生产代码完全复用原型 HTML。
- 不因为是原型就放弃可访问性、焦点态、错误态。
- 未经用户允许，不主动跑 Playwright 相关命令。

## 9. 反假两原则（默认遵守）

做"真交互"时，最容易踩的是"为了显得能用而造假"。真实感不是把假的做得更像，而是按真实产品的行为边界做——以下两条把这个边界讲清楚：

**原则 ①：不硬解析任意输入。** 真实 Agent 不会"输入任何话都能精准理解"。它认**有限几类意图**（如人群圈选：前 N 名 / 粘学号 / 阈值条件），命中就走对应流程；没命中就**澄清兜底**——"没完全懂，是不是这几个意思？"+ 几个 chips。原型照这个来，比假装全知更可信，也更接近上线效果。

**原则 ②：不假装全量重算。** 用户改了输入（移出一个学生、换一个口径），真实系统是**只更新几个可见的相关数字**（人数、命中数、均分），转一下"重算中…"再落定，大盘板块保持稳定。在演示用的假数据上假装"全量重新分析"，那才是假——既骗不过评审，也给后续埋下预期错位。

> 一句话：真交互 = 按真实产品的"能/不能、改什么动什么"边界做，不是把假数据算得更花哨。

## 10. 视觉与还原分面（注入式原型专用）

当原型是 fork 现网 SPA + 注入层（1→n 增量），"顶级视觉"和"还原现网"会打架。分面解决：

- **注入层（嵌在现网页里的部分）**：不能换审美方向。复用现网的 scoped 类名（如 Vue `data-v-*`）、配色、组件语言，目标是"看不出是后加的"。这一层"顶级"= 现网语言内的细节打磨（节奏、微状态、微排版），不是另起炉灶。
- **独立产出件（有自由度的部分，如导出的报告 HTML / 独立页面）**：这才是"顶级设计师审美"真正的舞台，可以推到一流 B 端产品水准。

**工具 override**：用 `ai-pm-frontend-design` 或外部 `impeccable` 打磨独立产出件时，若项目根的 `.impeccable.md` / `design-system.md` 是给**另一个产品**（如桌面客户端）写的，必须在调用 prompt 里**显式 override**「本文件绑定视觉 = 目标产品视觉指纹」，否则会把另一产品的配色/字体串进来。

**复用布局容器的坑（现网原生 + 自己的共享组件都算，不限注入式）**：复用任何 flex 行容器时，它的**布局假设也一起继承了**——容器是按某种"内容形状"设计的，塞进不符合假设的内容就会挤压/溢出。两类高频翻车（均亲历）：

- 往"只装单个全宽子元素"的容器（如现网 `.msg-bottom-row`）里塞**多块结构** → 被横向摊开、竖排单字、出滚动条。
- 往"标题 + 右侧短操作"的 space-between 卡头里塞**长内容**（如长副标题）→ 窄容器里被挤截断。

规避：复用任何行容器前，先核对**自己的内容形状是否符合它的布局假设**（尤其窄容器 + 长/多内容）；不符就**包一层自己的容器显式定 `display`/`flex-direction`**、换成竖排、或确认并覆盖继承的布局。别假设父容器适配你的内容——这条对复用现网类和复用自己的共享组件**一样成立**。

> 完整工作流见本机知识库 `playbooks/PLAYBOOK-010`（fork 注入式原型推到设计稿/可操作水准；本机沉淀，开源仓不含）。

## 11. 验证铁律：DOM 断言不替代视觉

经验教训：原型的"视觉/布局"是一等交付物，但 **DOM 断言（元素存在、计数、可见、类名、文本）只验"逻辑通了"，验不出"看着对"**。`querySelector` 找得到、count 对、`visible=true`，但 `flex-direction` 错了、溢出了、文字竖排了，断言照样全绿——纯视觉的布局 bug 用 DOM 检查根本检不出来。

所以验证（经用户允许跑浏览器时）必须：

- **每个关键状态都截图肉眼核对**：每道闸、每个异常态、每个产出件页面，逐个截图，在目标视口（如 1440px）看真实渲染。不是只截一两个状态、其余靠 DOM 断言。
- **重点看**：横向溢出/滚动条、文字折行或竖排、对齐错位、层级压盖、间距塌陷、窄面板下的挤压。
- **截图通过才算"复验通过"**：DOM 断言绿 ≠ 复验通过；没截图核对的状态，在审计里如实标"仅 DOM 验证，未视觉核对"，不要谎报"全过"。
- 截图本身能跑（如遇字体加载超时，等待后重试或截元素区域），不要因为"截图可能超时"就退回纯 DOM 验证——那正是漏掉视觉 bug 的根源。
