# Prototype Design Kernel

## 1. Context Gathering

生成前先在内部完成以下判断，不需要把过程全部输出：

- 产物类型：完整业务原型、单页面状态样张、注入式页面、独立报告页、客户端页面。
- 目标产品：当前原型服务的是哪个产品，不默认等同于 AI_PM 桌面客户端。
- 用户角色：主用户、协作方、审核方、管理方分别看什么、做什么。
- 设备形态：移动端、桌面 Web、响应式、混合页面。
- 核心任务：用户从哪里进入、完成什么动作、看到什么反馈。
- 约束来源：公司规范、视觉锚点包、代码仓指纹、PRD、用户偏好、项目根 `.impeccable.md`。

缺少信息时先用 PRD 和场景推断；会影响方向的未知项要写入假设，不把假设当事实。

## 2. Visual Source Priority

按以下顺序处理冲突：

1. 用户明确指定的设计规范或公司/团队规范。
2. `06-prototype-visual/visual-fingerprint.md` 和 ready 状态视觉锚点包。
3. `_memory/layout-shell.md` 等真实代码仓设计指纹。
4. PRD 中目标产品、用户角色、终端形态和业务流程。
5. `.impeccable.md` 的通用设计质量要求。
6. 情境化设计判断。

根目录 `.impeccable.md` 或 `docs/design-system.md` 若描述的是 AI_PM 桌面客户端，只能用于 AI_PM 客户端页面。生成其他业务原型时，不继承其品牌色、字体、圆角、导航结构。

## 3. Product Fingerprint

每个原型必须形成一个具体视觉主张，而不是“现代简洁”这类空话：

- B 端/运营工具：重扫描效率、稳定导航、密集但不拥挤的信息布局；避免营销 hero、过度插画、装饰渐变。
- 教育产品：强调学习进度、任务反馈、角色差异；教师侧偏管理效率，学生侧偏路径引导。
- Agent/hybrid 产品：必须呈现用户输入、AI 思考/执行中、工具失败、结果预确认、用户修改、人工接管。
- 数据分析产品：先让读者理解趋势和异常，再给明细；不要把图表当装饰。
- 移动端 C 端：优先路径流畅、拇指可达、明确反馈；避免桌面表格硬塞手机。

## 4. Layout Rules

- 页面一级结构必须稳定：导航、主内容、操作区、反馈区不要互相挤压。
- 固定格式元素要有稳定尺寸：按钮、筛选器、表格列、图表容器、状态面板不能因内容变化跳动。
- 不把 page section 做成大卡片；卡片只用于重复项、工具面板、列表项、弹窗或需要明确边界的内容。
- 不做卡片套卡片；如果信息层级复杂，用分组标题、分隔线、表格、tabs 或侧栏解决。
- 标题字号服从容器：面板内标题要紧凑，只有真正首屏 hero 才使用大号标题。
- 文本必须适配容器；长词、长数字、长标题要换行、截断或缩小，不允许重叠。

## 5. Interaction And States

核心流程至少覆盖：

- 默认态：主页面可读、主操作明确。
- 加载态：局部骨架或进度反馈，不用整页空白。
- 空态：说明为什么为空，并给出下一步动作。
- 错误态：用户可理解、可重试、可返回。
- 成功态：展示结果、影响范围和下一步。

交互必须改变真实 UI 状态。导航要在页面内切换；筛选要改变列表或图表；编辑要有草稿/保存反馈；AI 生成要体现运行中、结果确认和失败兜底。

## 6. HTML Implementation

- 优先单文件 HTML，CSS/JS 内联；CLI 多文件原型必须有 `manifest.json`。
- 不依赖远程图片、远程字体或必须联网的 CDN；必要图标用内联 SVG 或 CSS 简化表达。
- CSS 用语义化变量，但不要写回 PRD。
- JS 只实现原型需要的状态变化，不伪造复杂后端逻辑。
- 组件命名和假数据要贴近业务领域。
- 响应式要用稳定断点、grid/flex 约束和容器尺寸，不用 viewport 字号缩放。
