# Design Brief

生成 UI/HTML 前先形成内部 `Design Brief`。它不是给用户看的说明文，而是后续视觉、交互和文案判断的约束。

## 1. Extract From Existing Context

优先从以下来源提取，不要一上来问用户：

- PRD：目标用户、场景、核心任务、角色权限、端形态、关键状态。
- 项目记忆：产品定位、已定方案、不能做什么、历史偏好。
- 参考资料：竞品、截图、品牌规范、用户访谈、数据报告。
- `.ai-pm-config.json`：设计模式、设备类型、项目偏好。
- `.impeccable.md`：只提取通用质量要求；若它描述 AI_PM 客户端，不继承品牌视觉到业务原型。

## 2. Brief Fields

内部 brief 至少包含：

- `target_product`：本次原型服务的产品，不默认等同于 AI_PM。
- `target_users`：谁使用、什么经验水平、当时心态如何。
- `jobs_to_be_done`：用户要完成的 1-3 个核心任务。
- `usage_context`：使用地点、设备、频率、时间压力、协作关系。
- `tone`：界面应带来的感受，如可信、克制、高效、轻松、专业。
- `aesthetic_direction`：一句具体视觉主张，不写“现代简洁”。
- `anti_references`：明确不要像什么，包含用户禁忌和 AI 味反模式。
- `constraints`：公司规范、视觉锚点、代码仓指纹、设备、无障碍、性能。
- `open_questions`：会影响方向且当前无法判断的问题。

## 3. Ask Only When Needed

只有缺口会实质影响视觉方向或信息架构时才问用户。最多问 1-2 个关键问题：

- 谁是最核心的使用者？
- 这个界面要给人什么感觉？
- 是否有明确参考或反向参考？
- 本次更看重可评审、可演示、还是接近真实上线？

轻微缺口用假设补齐，并在内部标记为假设；不要把假设当事实。

## 4. Use In Prototype

`Design Brief` 必须影响：

- 页面优先级：首屏先解决用户最关心的任务。
- 密度：B 端、数据和教师管理场景可以密；学生/C 端要更引导。
- 视觉：色彩、字体、圆角、留白、图表和空状态要匹配场景。
- 文案：按钮、错误、loading、空状态按用户心态写。
- 交互：核心路径优先可操作，次级能力可渐进展示。
