# 产品验收判断卡

> AI / Agent 产品的「PM 意图层」验收方法论。开干前读一遍，验收过程随时回查。
> 定位：验「实现符不符合 PRD 意图」，AI 只给证据 + 草拟、人拍板；不替代 QA 回归。

---

## 一、两条命门（最重要，先记牢）

AI 产品验收跟传统功能验收最大的不同：**AI 输出不确定、还时好时坏**。下面两条是从真实翻车里换来的，违反了就会把错的结论推给老板。

### 命门 1 · 单次是假设，判定看分布

跑一次得到的结果（不管"好了"还是"坏了"）只是一个**假设**，不是结论。AI 同样的输入每次答得可能不一样、同一个功能这次正常下次出错。**判定要看分布——3 次里中几次（3/3 还是 1/4），而不是某一次截图。**

铁律：**P0 级问题、以及「研发说修好了/改善了」这类结论，都必须复现 ≥3 次再下。**

> 真实教训（通用化）：一轮验收里，有个问题单次看像 P0、复现 3 次却 0/3 没再现（其实是偶发）；另一个功能单次看"改善了"、复现 3 次却 3/3 还是坏的（单次是假象）；还有个问题单次自相矛盾、复现却正常。三次都靠"复现"在推给老板前拦住了。**单次就报，研发一句"偶发/环境问题"就能正当顶回来，而且他对。**

### 命门 2 · 别信自己脚本的绿勾

自动检测脚本只会查你叫它查的那几样。它可以打印「✅通过」，而一个**更严重的问题**就摆在 AI 回复的全文里、它没检测到。

铁律：**结论靠读 AI 回复全文，不靠脚本的绿勾。** 脚本的判定是「提醒你去看」，永远不是结论本身。

> 真实教训：脚本判过「✅修好了」，但 AI 回复正文里漏出了一大段不该给用户看的内部实现——脚本没检测那一项，是人读全文才抓到的。

---

### 命门 3 · 真跑留痕：无证据 = 该轮无效（2026-07-12 合并计划波2 N2）

**病根实证**：AI 会"声称测了但根本没操作界面"（2026-07 星光测评整批作废——"看都没看就直接开新一轮"），还会幻觉编造工具成功回显（同月《AI造假失效模式-复盘与防治.md》整场事故：报告"截图已归档 12/12 审计"实际 HTML 只有 8 行空壳）。**觉悟治不了机制病**，只能上不可绕过的外部证据。

三条铁律：

1. **主台账 = 「验收主张 → 操作证据 → 断言结果」三列**，每条验收记录一行；操作证据必须是文件系统里真实存在的东西（trace/截图/导出的 DOM 断言记录，带时间戳路径）——**空证据列 = 该轮无效，不许写"通过"**。
2. **留痕形态优先 Playwright tracing**：每测评轮 `context.tracing.start/stop` 落一个 trace.zip（自带每步截图+DOM 快照+时间戳）；收口时机器核对"trace 内 action 数 ≥ 声称交互轮数"（只证操作发生，**不证检查正确**——检查正确性仍靠台账断言列+人读）。
3. **三条边界**：①本机跑 Playwright 前仍须用户明确授权（老铁律不变）；②trace/截图含业务 DOM 与页面内容——一律落在项目 `14-acceptance/`（gitignore 区），权限勿宽，验收结束按保留期清理；③每次 Write/落盘后立刻 `wc -l`+grep 锚点实测（造假复盘 5.1），绝不把"没核实"写成"已完成"。

## 二、三类验法分流（验收清单每条都要标）

不同验收点，**验法和"谁拍板"完全不同**——这是 AI 产品验收和传统验收最大的区别。拆清单时给每条标一类：

| 标记 | 类型 | 怎么验 | AI 做到哪 / 人做哪 |
|---|---|---|---|
| 🖥️ | 确定性 UI | 浏览器走查 + 截图 | **AI 初筛**：给"流程通了/这步报错了"+ 截图，人扫一眼确认 |
| 🤖 | AI 行为 | 打一批输入（含边界/对抗），对 rubric 打分看落不落在可接受范围 | **人拍板**：同样的问 AI 每次答得不一样，AI 给"范围内/范围外"，对不对人定 |
| 📊 | 数据正确性 | 拿真值比对（查数据库/接口/指标）| **需真值**：AI 盯页面看不出"这条数据是不是真对"，得调真值核 |

**状态字段**：⬜待验 ／ ✅通过 ／ ❌不通过 ／ ⚠️存疑（AI 拿不准，需人看）。AI 永远不自己填 ✅。

## 三、六阶段详解

### 阶段 0 · 拆验收清单（纯通用、不依赖产品）
- 读 PRD → 拆成验收点，每条标三类验法（上一节）。
- 先定**环境前提**：测试环境常有"数据少/是 mock"的情况——数据层返回不足是环境问题、不算缺陷，先说清，免得误判。

### 阶段 1 · 连浏览器（硬闸）
- 打开验收浏览器（`scripts/start-browser.sh` 自动弹窗）→ 用户登录测试环境 → AI 用 Playwright 接管。
- 接管后先确认三件事：①连上了 ②页面是真渲染出来的（不是白屏）③关键入口能定位到。
- ⚠️ **连得上 ≠ 能驱动**：这步只证了"能读"，别据此就承诺"能自动验"——驱动得下一阶段先试通一个。
- 连不上 → 退手动验 + AI 记录提单。

### 阶段 2 · 先探测后驱动（每个产品做一次）
- **别假设 DOM**：驱动任何产品前，先照 §六的 probe checklist 摸清**这个产品**的锚点。
- 摸清了，先**驱动一个 case 试通整条链路**（输入→发送→等答完→读回复），再批量。"连上"到"能驱动"中间还隔着一层，先证通一个。

### 阶段 3 · 三类分流验收
- 🤖 构造输入 → 发送 → 等答完（§七）→ 读回复 → 对 rubric 判（§四）。
- 🖥️ 截图初筛留证。
- 📊 查真值比对。
- **写操作安全**：会改后端数据的操作（加入收藏/购物车、删除会话等）只在**测试账号**上做，且需用户**每次单独授权**——不是写死的常驻权限。只读验收（检索/查询）不涉及。

### 阶段 4 · 复现（见命门 1）
- 坐实的发现复现 ≥3 次，排混淆（会话有没有清干净、忙碌信号时机、上传有没有真成功）。
- 结论三档：**稳定复现**（写明 X/X）/ **偶发**（写明 1/N、留档观察、再现才升级）/ **通过**。

## 四、AI 行为 rubric 怎么打

AI 行为不能逐字对答案（同样的问每次答得不一样），要对**可接受范围**打分。给个样例，其余 🤖 项照此办：

**样例 · 信息齐全应直接执行**
- 输入：一个信息齐全、不该再追问的请求。
- ✅ 必须命中：把关键要素都识别对了（该有的字段一个不漏）。
- ✅ 必须：直接执行、不弹多余的二次确认。
- ⚠️ 可接受变体：话术措辞不同没关系，要素齐就行。
- ❌ 不可接受：漏了关键要素 / 弹了不该弹的确认 / 识别成了别的意图。
- 打 N 个变体（换措辞、换口语化表达、故意缺一个字段）看稳定性——这就是命门 1。

打 rubric 的精神：**列出"必须命中 / 可接受变体 / 不可接受红线"三档**，按红线判，不揪措辞。

## 五、复现纪律（命门 1 的执行）

- 同一个 case 自动跑 N 次（用 `scripts/playwright-runner.cjs` 的复现函数），统计分布。
- 每次之间要**隔离**（新建会话/清空），并验证真的清干净了（别让上一次的残留污染这一次）。
- 报结论带分布数字：「X/N 复现」「偶发 1/N」——别只说"复现了/没复现"。

---

## 六、probe checklist（先探测后驱动·找哪些锚点）

驱动任何新产品前，先探测、摸清这个产品的这几样（选择器每个产品都不同，必须现摸）：

1. **入口** — 怎么唤起 AI（浮标/按钮/输入框在哪）。
2. **输入框** — 是普通输入框还是富文本，选择器是啥。
3. **发送** — 发送按钮选择器 / 还是回车发。
4. **「忙碌信号」** — AI 响应中有什么可判断的状态（最常见：输入框被禁用置灰；响应完恢复可输入）。**这是判断"答完没"的关键，见 §七。**
5. **上传口**（如需验图片/文件类）— file input 选择器。
6. **结果容器** — AI 回复渲染在哪个容器（多轮对话的消息列表）。

摸的方法：连上后扫页面元素，把这几样的选择器记到项目侧 `_runner/`。摸不准就先 dump 结构、看截图。

---

## 七、完成检测：靠「忙碌信号」，不靠文字停没停

判断"AI 答完了没"——**别用"回复文字不再变化"来判**，会被「正在思考中…」「加载中…」这类静态占位骗（占位文字稳定，但 AI 根本没答完）。

**可靠做法**：gate 在产品的「忙碌信号」上——发送后等输入框**被禁用（响应中）→ 又恢复可输入（响应完）**，恢复可输入才算真答完。这个信号比文字稳定可靠得多。

> 这也是 `scripts/playwright-runner.cjs` 里"等答完"函数的做法。

## 八、输出规范（提单台账怎么写）

1. **问题描述写大白话现象**——说"什么情况下出什么毛病"（如「搜索结果说有，卡片却不出来」「找东西太慢，要等一分多钟」），让人一眼看懂。**技术细节（接口/字段/原理/选择器）不进描述列**，挪到说明页 `notes.md`。
2. **判定列永不自动填**——AI 填：序号/问题描述/截图/问题类型/优先级（草拟、标"待拍"）/提出人；**留空给人**：研发责任人、处理状态/通过与否。模板的 `fillRule` 写死这条。
3. **根因簇归类**——别把 N 条当 N 个独立 ticket 甩给研发。归成几个根因（A 渲染 / B 性能 / C 话术…），写进 `notes.md` 说明页，并告诉研发**先修哪个**（有的根因是硬闸，修了它能解锁一批被它阻断的验收项）。
4. **偶发要标清**——偶发问题标"1/N、留档观察"，别跟稳定复现的同等对待（命门 1）。

## 九、不替 QA 边界（别越界）

- 你验的是「实现符不符合 PRD 的产品意图」，**不是**代码质量、不是性能压测、不是接口稳定性回归——那些是 QA 的活。
- 单次能测的（如一次响应耗时）只能作"代理值"参考，P90/可用性这类统计指标单次测不出、要标"走压测/监控"，别拿单次当结论。
- 研发说"环境问题/已修"也要**实测验证**，别偏听——但验证后如果确实是环境/数据侧问题（如真值标签本身错），如实归到对应侧，别硬塞成产品 bug。
- **领域知识别想当然**（命门级）：被验的是专业产品（教育/医疗/法律…），很多"对不对"取决于领域知识，AI 极易拿**外行假设**把**正确行为误判成 bug**。真实教训：把"AI 对某知识点不追问、直接检索归类"当成 bug，其实那个知识点本就只属一个类别（如"数列"只在高中）、直接检索才对、追问反而错——是拿了"它该多问一句"的常识假设。**所以凡判断涉及领域知识（这知识点属哪个学段 / 这数据对不对 / 这流程合不合规），AI 只给现象 + 标存疑、让 PM 拍，别拿常识替判对错**。这是命门 2「AI 只给证据」在领域知识上的延伸。
- **结论前先自证测试有效**（命门级）：下「产品有问题」结论前，先排除是不是**自己测试的毛病**——① 外行假设（把正确行为当 bug，如不懂"数列只高中"）② 脏样本（如截图被浮层遮成残缺、上传半张题）③ 工具 bug（完成检测被"正在思考中"占位骗）。**脏输入 / 错假设跑出来的结果都不算数**。真实教训：一轮里连栽两次（领域假设 + 残缺样本），都不是产品问题、是我测试本身脏。跟命门 2「别信自己绿勾」同源——**先信得过自己的测试，再谈信不信结论**。

## 十、这套为什么这么设计（别当教条）

这些规矩的根都是一条：**AI 产品的输出不确定、会飘**。所以才要复现看分布、才不信单次和绿勾、才对 AI 行为打范围而非逐字对。换个确定性的传统功能，很多就不必这么重。判断该多严，看被验的东西有多"飘"。
