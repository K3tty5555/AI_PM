# 经验分享文章：公开来源结构规律

访问日期：2026-07-30

> 使用边界：这里只提炼通用规律，不复制原文、标题和平台模板，也不把平台规则当成唯一写法。运行 Skill 时不依赖联网。

## GitHub Docs

来源：[GitHub Docs 内容模板](https://docs.github.com/en/contributing/writing-for-github-docs/templates)

- 先判断内容用途，再选择结构；不要让一种模板承担所有写作任务。
- 开头尽快说明文章解决什么问题、适合谁读。
- 操作或方法类内容使用真实上下文，让步骤与目标相连。
- 固定必要结构，允许正文模块随内容变化。

## 知乎创作者手册

来源：[知乎创作者手册](https://www.zhihu.com/knowledge-plan/manual)

- 先形成清晰观点，再用材料支撑观点。
- 标题承诺要在正文兑现，避免只吸引点击却答非所问。
- 保持原创表达，引用外部材料时交代来源。
- 让内容对目标读者有实际信息增量。

## Devpost

来源：[Devpost 项目案例：SymptomStream](https://devpost.com/software/symptomstream)

- 用动机、做法、挑战、成果和学习串起一次实践。
- 具体选择和调整比抽象口号更能说明方法。
- 结果应回到最初问题，无法证明的效果不要补写。
- 踩坑不是附录，而是解释关键判断的证据。

## The Carpentries

来源：[The Carpentries 课程模板](https://github.com/carpentries/lesson-example)

- 学习目标、前置条件、练习和关键点适合教学材料。
- 内容可拆成可验证的小单元，便于学习者实践。
- 教学材料需要比独立文章更明确的活动和反馈机制。

The Carpentries 只作为未来培训材料参考，不进入经验分享文章首版结构。首版不生成培训讲义、课程教案或练习设计。

## 通用提纲示例

主题：如何让需求评审更有效

1. 开场：评审经常陷入什么具体困境；本文的核心判断是什么；读者能带走什么。
2. 主体一：一次真实评审暴露了哪些问题，证据是什么。
3. 主体二：做了哪些调整，为什么这样调整。
4. 主体三：结果如何，哪些变化能够确认，哪些仍只是推断。
5. 可以直接拿走的做法：整理成能脱离原项目使用的步骤或检查清单。
6. 适用边界：说明团队规模、素材条件和不适用情况。

这只是结构示例，不复制成固定标题；写作时根据素材保留两到四个真正承载内容的主体章节。
