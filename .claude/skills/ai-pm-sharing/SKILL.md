# 经验分享文章

## 守住核心原则

把文章写成没有参与原项目的人无需上下文也可独立阅读、理解和复用的内容。每篇经验分享文章都要有：

- 真实实践：区分发生过的事实、作者的判断、外部资料和仍待核实的推断。
- 明确观点：用一句话说明作者从实践中得出的核心判断。
- 读者收益：说明目标读者读完能解决什么问题或改变什么做法。
- 适用边界：说明方法成立的前提、不适用情况和证据限制。

不要把通用常识伪装成用户的亲历经验。不要虚构数字、反馈、引用、因果关系或项目细节。

## 先判断是否应该使用本 Skill

在以下请求中使用本 Skill：

- 把项目实践、方法心得或踩坑经验写成经验分享文章。
- 把零散笔记整理成其他产品经理可以独立阅读的完整长文。
- 把既有复盘或知识材料改写成有观点、有证据、可迁移的文章。
- 用户明确说“经验分享”“经验文章”“心得长文”或“对外分享文章”。

不要在以下请求中使用本 Skill：

| 用户主要意图 | 处理方式 |
|---|---|
| 项目复盘、回顾决策得失 | 路由到 `ai-pm-retrospective` |
| 沉淀知识库卡片、方法卡或坑点 | 路由到 `ai-pm-knowledge` |
| 整理本周工作或生成周报 | 路由到 `ai-pm-weekly` |
| 生成上线公告或操作手册 | 路由到 `release-docs` |
| 编写 PRD | 路由到 `ai-pm` 的 PRD 流程 |
| 培训讲义、课程教案、演讲稿或幻灯片 | 明确说明首版暂不支持，不要改写成文章交差 |

遇到组合请求时按意图顺序执行。例如“先复盘，再写成文章”应先完成项目复盘，再把经过确认的复盘和证据作为文章素材。本 Skill 可以读取复盘或知识库材料，但不要自动反向修改它们。

## 安全处理输入

只读取用户直接提供、上传或明确确认的素材路径。不要递归扫描无关项目来“补充背景”。

处理路径时：

1. 先检查路径是否存在、可读以及格式能否由当前工具可靠解析。
2. 对目录先解析真实根路径；逐项解析文件真实路径，跳过指向目录外的符号链接。
3. 对不存在、不可读、格式不支持或越界的项目逐项报告。
4. 不要猜测未读到的内容，也不要用通用知识代替缺失的用户经验。
5. 对客户名、内部产品名、接口、字段、账号、域名、策略、真实数字和截图先保留在私有区，并标记公开风险。

## 建立最低事实契约

用户要求“直接写”“马上成稿”时可以跳过提纲确认，但不能跳过事实清单。

先在 `_private/brief.md` 记录：

- 目标读者；
- 一句话核心观点；
- 读者可以带走的收益；
- 文章范围与不写内容；
- 当前最小素材缺口。

再在 `_private/source-notes.md` 分开记录：

- 已证实事实及其来源；
- 用户明确表达的个人经验或主观判断；
- 可公开的外部资料；
- 推断与待核实项；
- 内部信息及对应的公开表达。

只有主题、没有一手素材时，可以生成通用工作稿，但要明确它不是用户亲历经验，并保持 `draft`。不要把“我发现”“我常用”等第一人称经验写进缺少证据的文章。

## 按固定边界执行

### 1. 创建工作区

从仓库根运行：

```bash
python3 .claude/skills/ai-pm-sharing/scripts/create_article_workspace.py \
  "<文章主题>"
```

需要在指定仓库创建时显式传 `--repo-root PATH`。记录脚本输出的工作区绝对路径。不要手工拼接主题目录，也不要覆盖同名目录。

工作区只允许以下边界：

```text
_meta.json
_private/
  brief.md
  source-notes.md
  draft.md
  candidate.md
  assets/
publish/
  article.md
  assets/
```

只有 `publish/` 可以对外分享；不要把整个主题目录交付给外部读者。

### 2. 形成 brief 和事实清单

先写 `_private/brief.md` 与 `_private/source-notes.md`。素材不足时继续做可恢复的整理，但不要宣称文章已完成。

### 3. 选择叙事并给出提纲

默认使用仓库模板 `templates/sharing/experience-article.md`。需要判断文章结构时读取 `.claude/skills/ai-pm-sharing/references/source-patterns.md`；只提炼通用规律，不复制来源原文或平台模板。

推荐 2—4 个主体章节。根据素材选用实践过程、关键判断、方法框架、结果与证据、踩坑与调整或完整案例，不要把所有模块机械地列成固定标题。

用户没有要求直接写时，先给一版短提纲和一句话观点供确认。用户要求直接写时，直接进入工作稿，但仍执行事实契约。

### 4. 写工作稿

把工作稿写入 `_private/draft.md`。写作时：

- 先给观点，再解释过程。
- 用具体场景、动作和证据代替抽象口号。
- 把事实、个人判断和推断用准确语气区分。
- 将可复用方法写成脱离原项目也能理解的步骤。
- 不使用 PRD 的修订日志、需求范围、功能清单、详细功能设计和验收标准骨架。
- 删除模板注释、空章节和不适用模块。

### 5. 做语义检查

逐项检查：

1. 标题承诺是否在正文兑现。
2. 核心观点是否能由素材推出。
3. 数字、反馈、引用和因果关系是否有来源。
4. 内部名称是否已变成不泄密且不误导的公开表达。
5. 读者能否脱离原项目理解“为什么”和“怎么做”。
6. 可复用方法是否说明适用边界。

存在未核实事实、隐私风险或断裂论证时继续保留 `draft`，在交付说明中列出最小缺口。

### 6. 生成候选稿

只有语义检查通过后，才把终稿写入 `_private/candidate.md`。不要直接创建或修改 `publish/article.md`。

本地附件首版只使用 Markdown 内联链接：

```markdown
![说明](assets/URL编码文件名.png)
[附件说明](assets/URL编码文件名.pdf)
```

不要使用 HTML 本地图片、引用式本地链接、绝对路径、query string 或 `../`。先把候选附件放入 `_private/assets/`。

### 7. 检查并原子发布

先只读检查：

```bash
python3 .claude/skills/ai-pm-sharing/scripts/check_article_ready.py \
  "<工作区>" \
  --articles-root output/sharing/articles \
  --denylist scripts/.share-denylist \
  --strict
```

确认全部问题已处理后，再由同一脚本发布：

```bash
python3 .claude/skills/ai-pm-sharing/scripts/check_article_ready.py \
  "<工作区>" \
  --articles-root output/sharing/articles \
  --denylist scripts/.share-denylist \
  --strict \
  --promote
```

denylist 缺失或为空时不要自行加 `--confirm-missing-denylist`。只有用户明确确认该风险后才能加此参数。

脚本会先检查候选稿，在临时发布树中复制并复检，再原子生成 `publish/article.md`，最后把 `_meta.json.status` 更新为 `ready`。检查失败时保持 `draft`；不要绕过脚本手工发布。

修改既有文章时，只有用户明确给出既有工作区并要求替换，才使用 `--replace`。脚本会先把旧 `publish/` 保存在 `_private/`。

## 单独处理图片与附件

有附件时分别完成两项确认：

1. 逐张或逐份检查画面和可见内容，确认没有客户名、用户数据、内部地址、后台配置、账号或未公开数字；完成后传 `--confirm-visual-review`。
2. 检查文件元数据。本机有 `exiftool` 时让发布脚本检查并在发布副本上清除；没有工具时保持 `draft`，直到用户明确确认已用其他方式处理，再传 `--confirm-metadata-review`。

不要因为文件“看起来已经打码”就假设元数据也安全。脚本分别记录 `assets_visual_reviewed`、`assets_metadata_reviewed` 和 `assets_metadata_tool`。

## 谨慎校准语言

只有用户明确希望贴近个人口吻，或普通叙述段落存在明显 AI 腔时，才对局部段落使用 `humanizer-pm`。不要改动引用、数字、代码、表格、事实清单或来源。校准后重新运行事实、隐私、链接和附件检查。

## 交付结果

状态为 `draft` 时，说明：

- 工作稿或候选稿的私有路径；
- 仍缺哪些事实、证据或人工确认；
- 为什么尚未生成可分享稿。

状态为 `ready` 时，只把 `publish/article.md` 及其 `publish/assets/` 说明为可分享内容，并简要说明检查已通过。不要自动导出 DOCX/PDF，不要自动发布到知乎、公众号、飞书或其他平台。

## 避免常见错误

| 错误 | 正确处理 |
|---|---|
| 只有主题却写成第一人称亲历文章 | 写通用 draft，列出一手素材缺口 |
| 把复盘报告或 PRD 换个标题当文章 | 重新确定读者、观点、收益和叙事 |
| 对敏感名称做简单替换后直接外发 | 保留私有映射，运行 denylist 和附件检查 |
| 用未经核实的效果数字增强说服力 | 删除、降级为待核实项或补充来源 |
| 把模板全部章节机械填满 | 只保留真正承载内容的主体模块 |
| 手工复制到 `publish/` | 只用检查脚本原子发布 |
| 一次性“润色全文” | 只校准必要段落，并重新检查 |

## 发布前快速检查

- [ ] 目标读者、核心观点和读者收益明确。
- [ ] 事实、个人判断、外部资料和推断已分开。
- [ ] 没有虚构数字、反馈、引用或第一人称经历。
- [ ] 标题在正文中兑现。
- [ ] 方法可脱离原项目理解，并说明适用边界。
- [ ] 模板注释、待补项和 PRD 骨架已删除。
- [ ] 内部名称、链接和附件已通过严格检查。
- [ ] 图片画面与元数据分别确认。
- [ ] `publish/article.md` 由脚本生成，`status` 为 `ready`。
